summary: Workspace cleanup now records an already-clean teardown once as success instead of failing forever.
category: fix
dev: `task:reconcile-orphaned-workspace-worktree` gained fixed reason codes — `settled` (this pass removed something), `already-clean` (goal reached with nothing left to remove, `success:true`), `retained-unsettled` (a deliberate retention that stays addressable), `git-teardown-failed` (worktree list/remove/prune threw), `branch-evidence-failed` (the land-proof chain threw), and `branch-evidence-unknown` (the `show-ref` presence probe could not be answered) — so a genuine git failure stays distinguishable from an entry that was already reclaimed. Branch presence is probed with the canonical tri-state `probeRepoBranch` *before* the branch name is consumed by any land-proof command, which is why an already-deleted `fusion/<id>` branch reads as `absent` instead of throwing exit 128 and being labelled a failure; `not-evaluated` and `evidence-unknown` are non-proofs excluded from the settlement set, so absence of evidence never blanks a path. A settled or already-clean entry retires durably by blanking its disposable `workspaceWorktrees[repo].worktreePath`, and a card whose every recorded path is blank with no per-task directory is dropped by `hasWorkspaceTeardownWork()` before the guard chain: no git call, no merge-queue query, no audit row. The `repo:"task-directory"` row is now written only for an actionable disposition (`removed`, `retained`, `retained-legacy-layout`), deduped once per process, and reports `success:true` because a retention is not a failure.
