summary: Retry on a held planning key answers 409 naming the holder, and an operator can reclaim a dead holder's key.
category: fix
dev: Planning-lock refusals now carry structured detail instead of only a sentence: `PlanningLifecycleLockTransportError` gains `reason`, `phase`, `budgetMs`, `waitedMs`, `heldMs`, `maxHoldMs`, `holder` and `unresolvedPid`, and the canonical classifier sentences are unchanged so existing recovery paths keep matching. One end-to-end deadline bounds every phase of an acquisition (`timeoutMs`), a granted hold may be bounded (`maxHoldMs`), and teardown is verified from a second session rather than requested. New `TaskStore` surface: `withPlanningLifecycleLock(id, fn, { holderLabel, timeoutMs, maxHoldMs })`, `diagnosePlanningLifecycleLock(id)`, `releasePlanningLifecycleLock(id, { confirm, isCardLive, ageFloorMs })`, `listPlanningLifecycleHolderSessions()`; `OPERATOR_PLANNING_LIFECYCLE_LOCK_TIMEOUT_MS` (20s) is the operator-lane wait. New HTTP surface: `GET /api/tasks/:id/planning-lock` reads the holder, `POST /api/tasks/:id/planning-lock` with `{"confirm": true}` ends a provably abandoned holder's session; both answer 404 for an id that names no card. The terminate veto conjunction lives in the shared release surface, not in the caller: the holder must carry the `fusion-planning:` prefix this product stamped, sit past `PLANNING_LIFECYCLE_RELEASE_AGE_FLOOR_MS` (15 min, PostgreSQL-measured), not be running a statement or registered live here, and belong to a card the caller can prove idle — a missing or throwing `isCardLive` refuses. The route answers 200 only for `released` and `not-held`; `holder-active`, `live-session`, `card-live`, `below-age-floor`, `foreign-holder` and `identity-not-derivable` are 409, while `holder-query-failed`, `liveness-unproven`, `transport-unavailable`, `terminate-failed` and `release-unproven` are 503. A self-healing pass `reconcile-planning-lifecycle-orphan-holders` ends only sessions that pass the same conjunction (it supplies the card-liveness probe rather than duplicating the check), and it moves no card and writes no lifecycle status. Sessions are labelled through `application_name` (`fusion-planning:<lane>[:<taskId>]`), which is the only way a holder can be attributed to a card, since an advisory key is a `hashtext()` digest.
