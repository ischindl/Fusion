summary: Board stays responsive while the engine is busy: the DB pool default rose 3 to 10, and /metrics shows pool occupancy.
category: performance
dev: `DEFAULT_POOL_MAX` is now 10 per store (was 3), sized to the documented default engine-lane footprint — `maxConcurrent` executors plus the planning, plan-review, code-review, merge and scheduler/heartbeat lanes — with >= 3 slots left for dashboard HTTP reads; `FUSION_PG_POOL_MAX` resolution (1..500) and the dedicated `max: 1` migration/health sessions are unchanged. Measured on a production board: `GET /tasks/page?limit=100` 10.8-17.1 s -> 3.3-3.9 s, `GET /tasks/board-workflows` 26-32 s -> 4.3-9.8 s. Every Fusion backend now carries an `application_name` (`fusion-runtime:<projectId>`, `fusion-health:<projectId>`, `fusion-migration`), the external-mode startup line prints `runtimePoolMax=N`, and `/metrics` serves `fusion_postgres_pool_backends{project,role,state}` plus `fusion_postgres_pool_max{project,role}`, read on the dedicated health session so the probe never queues behind the pool it measures. **CAVEAT — this retires a documented protection:** the old default existed because external databases frequently impose a low connection quota. Deployments whose PostgreSQL/role quota is below `stores × (poolMax + 2)` must set `FUSION_PG_POOL_MAX` lower or startup connection acquisition is refused outright (`FATAL: sorry, too many connections for connection pool`, a reserved-slot refusal, or a role-connection-limit refusal) instead of merely running slow. See `docs/settings-reference.md` and `docs/multi-project.md`.
