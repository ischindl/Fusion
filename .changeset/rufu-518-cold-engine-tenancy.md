summary: A merge on a card in a still-starting project now says retry in a few seconds instead of task not found.
category: fix
dev: Merges are one instance of a route-layer tenancy rule — a request that names a project may only mutate inside that project. `getProjectContext` resolves the store for the named project correctly even while its engine is cold, but the engine and the process-default callbacks derived from the launch engine (`onMerge`, `automationStore`, `routineStore`, `routineRunner`, `engine`) are not, so a cold second project was served by the launch project: `POST /api/tasks/:id/merge` answered `500 {"error":"Task <id> not found"}` in ~0.05 s for a card that `GET /api/tasks/:id` returned 200 for at that moment. One exported predicate (`namesForeignColdProject`, `packages/dashboard/src/routes/context.ts`) now decides "foreign and cold" for the new required `ProjectContext.launchScoped` flag, the merge route, and the automation/routine resolvers, so they cannot disagree. A foreign-and-cold request gets `503` + `Retry-After` + `details.code = "engine-starting"` + `retryable: true`, having proven it called neither the launch callback nor `store.mergeTask` — the latter was the worse leg, since it lands a card with `mergeConfirmed: false` and no merge. Also closed on the same predicate: project-scoped Automations/Routines listing, and routine **execution**, which previously ran in the launch project; and the three remote login-URL / QR sites, which minted a token from the named project's store and addressed it at another project's tunnel host. Unscoped requests, the launch project's own id, warm engines, the `--no-engine` host's `uiOnlyOnMerge` path, and `POST /tasks/:id/retry` on a cold engine are unchanged; no engine is pre-started and scoped reads stay non-blocking. A comment-stripped static ratchet (`project-tenancy-launch-callback-ratchet.test.ts`) forbids new launch-object fall-throughs in project-scoped routes. Scripted drains: a `Task <id> not found` arriving in well under a second on a card that reads back is cold-engine noise to retry, never a deletion to act on. Documented in `docs/multi-project.md` → Request tenancy and `docs/dashboard-guide.md` → Merging a card in a project that is still starting.
