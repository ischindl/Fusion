summary: A stuck executor step re-runs itself in place instead of stranding its card with no way back.
category: fix
dev: Split two authorities that used to be one. A lifecycle move still needs containment approval; an **execution re-arm** (`attemptExecutionRearm` in `packages/engine/src/executor/execution-rearm.ts`) changes no column and no status — it installs a runnable task continuation at the same `step-execute` node so the scheduler re-enters the same step, which containment cannot refuse because nothing moves. It grants that only on `occupied` checkout proof (dirty tree or commits ahead, via the shared per-repository prover; `unknown` is never proof, so an uncommitted diff can never be discarded by guessing), validates the node against the card's current IR, claims its slot under the per-task advisory lock *before* seeding through `replaceActiveTaskWorkflowContinuation` (`onlyIfNoActiveTaskContinuation`), and clears `status`/`error` only after the seed lands — the RUFU-291 failure mode was a badge clear with no runnable row behind it. The loop is bounded by the persisted `mergeDetails.executionRearm` ladder (4 re-arms per unchanged signature; refusals counted separately up to 20 so containment's own repetition cannot spin forever) and ends in one sticky terminal park with a single `logEntryOnce` operator notice, so a card polled every 45 s cannot produce hundreds of identical lines. Re-arm reasons are a closed set (`step-failed` plus the stranded-recovery reasons) — a revision reason is deliberately refused, because a review `REVISE` owns a contained backward move and must not be replaced by re-running the step that produced the findings. Companion fix: the planner overseer now measures executor inactivity from the card's latest execution evidence (row clock, newest step-result lease/completion, `TaskStepReport.recordedAt`) and treats a live executor session as activity, so "no execution activity" can no longer broadcast hourly across steps that are finishing.
